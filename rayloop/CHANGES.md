# RayLoop —— 相对原版 gauntlet-loop 的改动说明

基于一次 20 部件 / 70 轮评审的实跑。每条改动都对应实际踩过的坑,不是推测。

## 新增(按重要性)

### 1. 「正确性先于品味」——最重要的一条
原版让 critic 判断好不好看。但长跑里最大的几次跃迁全部来自**接线 bug**,
不是审美:
- 所有 patch 过的材质共用一个编译后 shader → builder 调了 4 轮材质,从未被求值
- 后坐力被除以 10000 → 连发帧和静止帧像素级相同
- 一个配置值被读取但从未定义 → 每把武器瞄准偏移是 NaN,critic 判为「全项目最差画面」
- 色调曲线在暗部提升前钳位 → 326,816 像素被剪成纯黑,细节先被正确渲染再被销毁

这些全都长得像美术���题。只判断美感的 critic 会永远描述症状。

### 2. 说清楚这个 bar 到底能不能赢
浏览器渲染器不可能在建模上赢过有美术团队的 3A。这不代表 bar 选错了——够不到的
bar 依然在拉高工作。它代表**退出条件**错了。原版只有「赢了才停」,配上够不到的
bar 就是永不退出。新增区分:winnable(赢了就停)vs asymptotic(没有可修的
真实 gap 就停)。

### 3. 量而不是瞄
「枪太暗」不可执行;「14 个手部件 0 个露出武器实体,每根手指在木头里 17-23mm」
可执行。要求循环早期就建仪器:确定性截图、数值 diff、针对当前问题的专用探针。

其中一半是防自己的 agent:实跑中一个 builder 测出「40% 像素变化」,然后用
**完全相同的 shader** 截两次得到 44%——指标全是噪声。它诚实上报了这一点。

### 4. 也不要盲信 critic
critic 报「武器 51% 在画面外」,实测 93% 在画面内。它的**结论方向**对,
但**给出的理由**错,照着理由改就是错的。另一次报「所有怪物变体像同一个物种」——
对它拿到的那张图成立,因为截图工具一直在刷同样两个原型。生成器没问题。

规则:critic 判断产物,不判断代码。它对**现象**的观察通常准,对**成因**的
解释经常错。派活前先廉价验证。

### 5. 只评当前磁盘上的东西
一个 critic 花了整轮批评「手不见了」「没有阴影」,两者都在四十分钟前修好了。
它靠文件时间戳自己发现的,这一轮废了。改法:让对比工具自己重新生成产物,
把时间戳写进答案 key,让「用旧图」不可能发生而不只是不推荐。

### 6. 多 builder 并行的现实问题
一个文件一个 owner(两个 agent 编辑同一文件会静默互相回滚)、一个文件坏了
全员阻塞(需要快速语法门禁)、agent 会死(不能假设派出去的活落地了)、
跨部件的 bug 归 lead 修一次然后通知所有人。

## 改动

- 提示词长度 120-180 词 → 150-220 词。加了正确性和仪器那两句,值这个成本。
- 模板里加了两句:功能性检查、确定性截图+diff。
- 「什么会毁掉 loop」从 5 条扩到 9 条。

## 保留未动

bar 的三项测试(命名/可获取/可比较)、盲测抹标签、harsh critic 二选一而不是
打分、绝不用轮数当退出条件、最小化指令。这些是这套东西真正管用的核心,
实跑中全部验证有效——尤其盲测:critic 在 5 次盲选中全部正确认出真游戏。
